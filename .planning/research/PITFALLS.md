# Pitfalls and Threat Model Research

**Domain:** Local-first Rails verification framework and CI merge gate
**Project:** LineClear
**Researched:** 2026-08-16
**Confidence:** MEDIUM — recommendations are derived from current primary sources, but several product policies and cross-platform containment details still require ADRs and implementation validation.

## Executive Risk Rule

LineClear's highest-risk failure is a false `PASS`: the gate claims sufficient evidence even though a required analyzer did not produce complete, fresh, valid evidence. Gate status and run completeness must therefore be separate concepts.

Every configured analyzer run must end in exactly one explicit state: `succeeded`, `disabled`, `unavailable`, `unsupported`, `timed_out`, `failed`, `output_limited`, `invalid_output`, or `incomplete`. A run may return `PASS` only when every analyzer required by policy is `succeeded`, every required artifact is fresh and complete, and policy evaluation itself succeeds. Optional or intentionally disabled evidence must remain visible in the result manifest; its absence must never be described as coverage.

This fail-closed rule is an architectural contract, not adapter-specific error handling. RuboCop and Brakeman demonstrate why: their exit codes have different meanings, including ordinary findings, invalid configuration, recoverable scan errors, no scan, and internal failure. Each adapter needs a versioned exit-code and output contract rather than a generic `zero = pass, non-zero = fail` rule.

## Threat Model Foundation

### Assets to Protect

| Asset | Integrity or confidentiality requirement |
|-------|------------------------------------------|
| Gate decision | A `PASS`, `WARN`, or `FAIL` must be derived only from complete declared evidence and versioned policy. |
| Evidence manifest | Analyzer identity, version, command arguments, terminal state, timestamps, commit, output-limit state, and artifact digests must be auditable without exposing secrets. |
| Baseline and fingerprints | Existing debt must not be silently enlarged, mis-correlated, or reclassified by algorithm drift. |
| Policy, configuration, and waivers | Precedence, ownership, expiry, and effective values must be unambiguous and reviewable. |
| Repository source and secrets | Analyzer output, logs, AI context, caches, CI artifacts, and release packages must not disclose confidential material. |
| CI and publishing credentials | Untrusted repository or fork content must never execute with privileged tokens or publishing authority. |
| Published gem and release assets | The tested artifact must be the artifact published, with verifiable source and build provenance. |

### Trust Boundaries

1. **Repository boundary:** source, configuration, comments, fixtures, Git metadata, PR text, and analyzer configuration are untrusted input.
2. **Analyzer boundary:** executables, plugins, dependencies, exit statuses, stdout, stderr, paths, encodings, and structured output are untrusted. Running an analyzer may execute repository code; LineClear must not imply portable sandboxing it does not provide.
3. **Host boundary:** local execution inherits real CPU, memory, filesystem, process, and environment risks. The process runner can reduce exposure but is not an operating-system sandbox.
4. **AI boundary:** any remote transmission crosses a confidentiality boundary; model responses are untrusted advisory data and never objective evidence.
5. **CI boundary:** fork code and artifacts are attacker-controlled. Base-branch workflows, repository secrets, release environments, and write tokens are privileged.
6. **Release boundary:** built gem contents, checksums, attestations, tags, and registry publication must form one traceable chain.

### Relevant Threat Actors

- An accidental contributor who misconfigures an adapter, refreshes a baseline incorrectly, or publishes stale artifacts.
- A malicious fork contributor who controls source, filenames, configuration, test code, analyzer output, PR text, and workflow changes.
- A compromised analyzer, gem, plugin, GitHub Action, runner, AI provider, or maintainer account.
- A cost or resource abuser who creates large output, slow scans, pathological inputs, or repeated remote-AI requests.

## Critical Pitfalls: False `PASS` and Evidence Integrity

| ID | Pitfall and consequence | Warning signs | Prevention | Verification evidence | Phase / release gate |
|----|-------------------------|---------------|------------|-----------------------|----------------------|
| FP-01 | **Unavailable or unsupported analyzer becomes an empty success.** A missing executable, failed version probe, or unknown output version yields zero findings and therefore `PASS`. | `0 findings` with no analyzer version; missing command in `doctor`; version parse fallback; adapter accepts versions it never tested. | Require availability and version detection before execution; maintain an explicit supported-version range; represent unavailable and unsupported states separately; fail when policy marks the analyzer required. | Contract fixtures for missing executable, unparsable version, lower and upper unsupported versions; JSON result contains analyzer state and detected version; no `PASS` in required cases. | Phase 1 defines semantics; Phase 2 applies them to every adapter. Required evidence cannot pass any release gate. |
| FP-02 | **Timeout becomes success or leaves an analyzer running.** The parent stops waiting while descendants continue mutating files or consuming resources. Ruby warns that its generic `Timeout` facility cannot enforce timeouts on untrusted blocks. | Duration ends exactly at timeout but status is `0`; child PIDs remain; locked coverage files; later runs see unexpected output. | Use an external monotonic watchdog; launch a process group; on timeout send `TERM`, wait a bounded grace period, then `KILL`; drain pipes, reap the child, clean temporary state, and emit `timed_out`. | Integration fixture spawns a grandchild that ignores `TERM`; test proves both processes disappear, status is `timed_out`, cleanup occurs, and required policy fails. | Phase 1. No analyzer adapter ships until timeout and orphan tests pass on every supported OS. |
| FP-03 | **Non-zero exit is flattened or ignored.** Findings, invalid configuration, partial scan errors, or internal failures are all misclassified. | Adapter rescues any non-zero status and parses whatever exists; one generic exit map shared by all tools; stderr contains fatal text while decision is `PASS`. | Version each adapter's exit-code map; parse output only for statuses documented as producing valid complete results; preserve exit and signal metadata; treat unknown statuses as failure. | Table-driven adapter tests for every documented exit code plus an unknown code; evidence records raw exit status, mapped meaning, and parser disposition. | Phase 1 contract; Phase 2 per adapter. Unknown or failure status from a required analyzer blocks. |
| FP-04 | **Empty, malformed, partial, or parser-rejected output becomes “no findings.”** A crash after writing a valid prefix is especially dangerous. | Empty stdout with success; JSON followed by junk; missing summary or end marker; parser rescue returns `[]`; output count disagrees with summary. | Require syntactic parse and versioned schema validation; validate required fields, types, totals, and invariants; reject trailing bytes and partial documents; never rescue to an empty finding list. | Golden fixtures for empty, whitespace, truncated JSON at every structural level, invalid UTF-8, duplicate/unknown critical fields, inconsistent totals, and valid zero findings. | Phase 1 schema and parser contract; Phase 2 adapter conformance gate. |
| FP-05 | **Large output is truncated into a plausible result or exhausts memory/disk.** | Memory spikes; logs end mid-object; output-limit warnings without failed status; terminal or JSON output exceeds configured bounds. | Stream stdout and stderr concurrently with independent byte limits; cap nesting, strings, finding counts, and diagnostic retention; terminate the process group on overflow; mark `output_limited`; never parse a truncated artifact as complete. | Fixture emits unlimited stdout and stderr concurrently; bounded peak memory and artifact size; explicit limit metadata; required gate fails without deadlock. | Phase 1 safe runner. Output-limit behavior is a release-blocking contract test. |
| FP-06 | **Skipped, filtered, focused, or zero-test runs appear green.** A test framework can report zero failures while executing too little. | Zero runs; unexpected skip or pending count; focus/filter flags; expected suite absent; test count drops sharply without code deletion. | Normalize run, assertion/example, failure, error, pending/skip, and duration counts; record selection arguments and suite identity; support policy for zero tests, maximum skips, and expected suites; distinguish “tests passed” from “test command exited zero.” | Synthetic Minitest and RSpec fixtures for all-pass, skips/pending, focus/filter, zero tests, load error, and aborted suite; manifest proves expected suites ran. | Phase 2 testing adapter. Required suite completeness blocks merge. |
| FP-07 | **Stale or partial coverage satisfies policy.** SimpleCov caches and merges result sets; parallel finalization can proceed with arrived workers and skip threshold checks. | Artifact commit differs from `HEAD`; timestamp predates the run; worker count is short; coverage rises after test failure; internal `.resultset.json` is treated as a public contract. | Consume the versioned public `coverage.json`, not internal result-set shape; require schema, commit, root, run identity, and freshness match; isolate coverage directories per run; declare expected workers/suites; accept coverage only after successful complete tests and final collation. | Fixtures replay old coverage, mix commits, omit a worker, time out a worker, and reuse a dirty directory; each is rejected. A parallel happy path proves thresholds run after collation. | Phase 2. Changed-code coverage cannot gate until artifact freshness and completeness tests pass. |
| FP-08 | **Stale baseline or wrong comparison revision hides introduced debt.** | Baseline commit is not an ancestor; merge base silently falls back; target branch is inferred differently locally and in CI; generated baseline has no tool versions. | Version baseline metadata; bind it to fingerprint version, policy version, repository identity, and source revision; resolve and report the comparison base explicitly; fail on missing or ambiguous merge base. | Tests for shallow clones, rewritten history, unrelated histories, detached HEAD, renamed default branch, and baseline from another repository. | Phase 3 baseline contract; Phase 4 Git context. Ambiguous comparison base blocks changed-code mode. |

## Critical Pitfalls: Fingerprints, Baselines, Waivers, and Determinism

| ID | Pitfall and consequence | Warning signs | Prevention | Verification evidence | Phase / release gate |
|----|-------------------------|---------------|------------|-----------------------|----------------------|
| BL-01 | **Fingerprint drift after irrelevant edits.** Path and line fingerprints turn existing findings into introduced findings after formatting or nearby edits. | Large introduced/resolved pairs after adding comments; fingerprints change while analyzer, rule, and logical code are unchanged. | Use a versioned composite of analyzer, normalized rule, logical Ruby scope, normalized evidence, and controlled location context; exclude line numbers and volatile messages from primary identity; retain explainable components for debugging. | Mutation corpus adds comments, whitespace, lines, and unrelated methods; fingerprints remain stable and state remains existing. | Phase 3. Fingerprint stability corpus is a release gate for every algorithm change. |
| BL-02 | **Semantic collision merges distinct findings.** Even with SHA-256, identical normalized inputs can describe two real findings; truncating hashes increases collision risk. | One fingerprint maps to multiple current locations; finding count drops after normalization; baseline suppresses both copies of duplicated code. | Use full SHA-256 over a canonical length-delimited payload; detect duplicate fingerprints within a run; include a stable disambiguator when needed; never allow one baseline entry to suppress multiple live findings silently. | Fixture duplicates the same offense in two scopes/files and intentionally injects a hash stub collision; system reports ambiguity or unique identities, never one suppressed finding. | Phase 3. Collision behavior and fingerprint payload require an ADR before implementation. |
| BL-03 | **Rename and move handling trusts Git heuristics as identity.** Git rename detection is similarity-based, configurable, limited at scale, and does not provide general directory-rename semantics for ordinary diffs. | Delete/add pairs instead of rename; behavior changes with `diff.renameLimit`; copied finding is mistaken for moved; directory move produces mass churn. | Treat Git rename status as correlation evidence, not canonical identity; use `-z` machine output, explicit rename settings, and content/logical-scope matching; represent uncertain correlation instead of guessing. | Corpus covers exact rename, rename plus edit, copy, split, merge, directory move, rename-limit exhaustion, and unusual filenames. | Phase 3 fingerprint design plus Phase 4 Git adapter. Rename corpus blocks PR-readiness exit. |
| BL-04 | **Baseline poisoning absorbs new debt.** A contributor updates the baseline in the same change, or `check` mutates it automatically, making violations “existing.” | Baseline grows in ordinary feature PRs; no before/after summary; baseline generated from a failed or incomplete run; review cannot identify added entries. | Make checks read-only; require an explicit baseline-create/update command from a complete run; emit a signed-by-content diff summary of added, removed, and changed entries; protect baseline changes with designated review and forbid update in untrusted privileged CI. | Test that `check` never writes; poisoned baseline fixture is rejected when run metadata is incomplete or mismatched; repository rules require review for baseline path. | Phase 3. Baseline authority and review policy require an ADR; every baseline-changing PR gets a separate gate. |
| BL-05 | **Waivers become permanent or broad suppressions.** Rule-, directory-, or analyzer-wide exceptions erase visibility. | Missing owner/reason/expiry; wildcard scope; expiry parsed in local timezone; expired waiver still suppresses; waiver points to no live fingerprint. | Bind waivers to exact fingerprint and fingerprint version; require owner, reason, creation date, UTC expiry, and optional issue; reject broad scopes in the initial format; report unused and near-expiry waivers; make expiry deterministic. | Boundary tests just before, at, and after expiry; invalid dates; orphaned waiver; fingerprint migration; no wildcard accepted. | Phase 3. Expired waiver behavior (`FAIL` recommended for blocking findings) needs an ADR. |
| BL-06 | **Ambiguous or executable configuration changes policy silently.** Unknown keys, implicit YAML types, environment overrides, multiple files, or ERB/object deserialization produce different effective policy. | Typo is ignored; local and CI effective configs differ; config depends on current directory or ambient environment; loading config runs code. | One versioned config file; safe data-only YAML loading with no ERB or object tags; strict schema with unknown keys rejected; documented precedence; normalized project-root paths; `doctor` and JSON output expose redacted effective configuration and source of each value. | Fixtures for unknown keys, duplicate concepts, YAML aliases/tags, symlink escapes, invalid encodings, alternate working directories, and conflicting CLI/config values. | Phase 1. Configuration precedence and safe-load rules require an ADR before public CLI stabilization. |
| BL-07 | **Nondeterministic inputs produce different gates.** Time, locale, timezone, filesystem order, process completion order, random seeds, absolute paths, environment, and analyzer versions leak into identity or ordering. | Identical run manifests yield different JSON or exit status; finding order changes; fingerprints contain temp paths; failures reproduce only in one locale. | Canonically sort findings and map keys; normalize repository-relative paths; use monotonic time only for duration; keep display timestamps out of fingerprints; pin/record analyzer versions; constrain environment; record random seeds; define how analyzer nondeterminism invalidates evidence. | Replay identical fixtures under varied locale, timezone, path, CPU count, process order, and hash iteration; canonical result excluding documented volatile fields is byte-identical. | Phase 1 deterministic core; Phase 2 each adapter; Phase 9 cross-platform reproducibility gate. |

## Critical Pitfalls: Process Execution and Host Safety

| ID | Pitfall and consequence | Warning signs | Prevention | Verification evidence | Phase / release gate |
|----|-------------------------|---------------|------------|-----------------------|----------------------|
| EX-01 | **Shell injection through command, paths, or options.** Repository-controlled filenames or config become commands. | `system(string)`, backticks, `sh -c`, interpolated command strings, or shell escaping used as the primary defense. | Invoke a fixed executable with an argument array through `Process.spawn`/Open3; never invoke a shell; validate adapter-owned command and option structure; use `--` where supported before paths; reject arbitrary command strings in configuration. | Injection corpus includes spaces, quotes, semicolons, substitutions, newlines, leading dashes, Unicode, and NUL attempts; fixture proves literal argument delivery. | Phase 1. Static scan and process-runner tests block release. |
| EX-02 | **Ambient environment, descriptors, or logs leak secrets.** An analyzer inherits credentials and sockets or LineClear prints environment values. | Full `ENV` passed through; CI secret names visible in debug output; child inherits nonstandard file descriptors; commands include tokens. | Build a minimal documented environment allowlist; use `unsetenv_others` where supported; set `close_others`; pass secrets only when explicitly required by a trusted adapter; redact by key and value; never include secret values in commands, cache keys, diagnostics, or artifacts. | Canary-secret integration test asserts absence from child environment, stdout/stderr, JSON, cache, and temp files; descriptor fixture cannot access a parent-only FD. | Phase 1. Environment allowlist and platform exceptions require an ADR. |
| EX-03 | **Temporary files survive, race, or expose source.** GC-based cleanup is late and abnormal exit leaves data behind. | Predictable temp names; world-readable permissions; cleanup only in finalizers; residue after interrupt; shared temp directory between concurrent runs. | Prefer block-form `Tempfile.create`/`Dir.mktmpdir`, permission `0600`/`0700`, anonymous files when paths are unnecessary, per-run directories, and cleanup in outer `ensure`; do not place secrets in filenames. | Tests cover success, parser failure, timeout, `INT`, `TERM`, and concurrent runs; no residue after recoverable termination and permissions are restrictive. | Phase 1 safe runner. Document that `SIGKILL` cleanup cannot be guaranteed; startup may remove verified stale LineClear-owned directories. |
| EX-04 | **Signal and orphan handling is incomplete.** Killing only the direct PID leaves grandchildren, zombies, and pipe writers. | CI job ends but processes remain; wait thread hangs; zombie processes; output pipe never reaches EOF. | Start a new process group; trap termination in the parent; forward `TERM`, then bounded `KILL`; close stdin, drain both output pipes, wait/reap, and restore parent signal behavior. Define Windows behavior separately. | Grandchild, ignored-signal, closed-pipe, and parent-interrupt fixtures assert bounded shutdown and reaping. | Phase 1. Supported-OS containment matrix is an unresolved decision and ADR. |
| EX-05 | **Analyzer or crafted repository exhausts host resources.** CPU, memory, file descriptors, output, disk, subprocesses, and concurrent analyzers are unbounded. | Runner OOM; disk fills with reports; analyzer forks heavily; parallel default saturates CI; very deep JSON stalls parser. | Bound wall time, output bytes, artifact bytes, finding count, JSON depth/string length, concurrency, and retained diagnostics; apply OS resource limits such as CPU, address space, file size, and open files where available; make degraded controls explicit on unsupported platforms. | Stress fixtures hit each limit independently and together; LineClear remains responsive, reports the exact exceeded limit, cleans up, and does not `PASS`. | Phase 1 runner; Phase 2 adapter budgets. Performance and containment tests gate release. |
| EX-06 | **Malicious analyzer output attacks terminals, logs, paths, or reporters.** ANSI/control sequences forge prompts; CRLF forges logs; paths escape the repository; huge messages poison downstream systems. | Terminal clears or cursor moves; multiline messages mimic gate output; absolute/`..` paths; invalid Unicode; reporter writes outside output directory. | Treat all analyzer fields as data; validate encoding and schema; normalize and constrain paths to repository root; cap fields; escape control characters for console/log contexts; generate JSON through a serializer; never render raw Markdown/HTML; keep bounded raw diagnostics separate with restrictive permissions. | Fuzz corpus covers ANSI, CRLF, bidi/zero-width controls, invalid UTF-8, path traversal, absolute/URI paths, deep nesting, and oversized fields across console and JSON reporters. | Phase 1 reporters and Phase 2 adapters. Fuzz suite blocks machine-interface release. |
| EX-07 | **LineClear implies sandboxing that it does not provide.** Tests and analyzers may execute application code, plugins, initializers, or compromised dependencies with the user's authority. | Documentation says “safe” without scope; untrusted fork runs on a persistent or internal runner; network/filesystem isolation is assumed from subprocess use alone. | State the trust model plainly: argument isolation is not process sandboxing. Run fork code only on ephemeral isolated CI without secrets; do not use privileged or internal self-hosted runners. Consider optional OS sandbox adapters only after a dedicated design and ADR. | Documentation threat-model review; CI fixture verifies no secrets and read-only token; manual runner configuration review before enabling public forks. | Phase 0 security model and Phase 4 CI. Any stronger sandbox claim requires proof on each supported platform. |

## Critical Pitfalls: Optional AI Boundary

| ID | Pitfall and consequence | Warning signs | Prevention | Verification evidence | Phase / release gate |
|----|-------------------------|---------------|------------|-----------------------|----------------------|
| AI-01 | **Source or secrets are transmitted without meaningful consent.** Broad context collection crosses the remote-provider boundary. | AI turns on from environment alone; whole files or repository archives are sent; no request preview; ignored secret-scan warning; provider retention is undocumented. | Default AI to off; require explicit remote opt-in; build the smallest deterministic context; exclude sensitive paths before content scanning; fail closed on suspected secrets; show a redacted transmission manifest containing files, ranges, byte/token counts, provider, model, and retention link before or with the request. | Canary secrets in filenames, contents, diffs, environment, Git history, and generated files never reach a mock provider; snapshot proves only declared ranges are sent. | Phase 6. AI data boundary, consent granularity, and provider-retention requirements need an ADR before implementation. |
| AI-02 | **Repository prompt injection changes behavior or exfiltrates data.** Comments, docs, fixtures, PR text, and analyzer messages instruct the model. | Prompt concatenates repository text with instructions; model selects extra files or tools; output requests commands or uploads. | Delimit and label repository material as untrusted data; keep file selection deterministic outside the model; expose no write, shell, network, or secret-bearing tools; use least privilege; assume prompt injection cannot be perfectly filtered. | Adversarial fixture text requests instruction override, extra-file access, secret disclosure, and tool execution; mock records show no added context or capability and result stays advisory. | Phase 6 threat-model gate. Any future repair/agency feature needs a new ADR and security review. |
| AI-03 | **Invalid or persuasive model output changes objective truth.** Prose parsing, hallucinated findings, or malformed structured output affects the gate. | AI output overwrites severity/state; parse failure crashes `check`; model recommendation changes exit code; AI and deterministic findings look identical. | Validate responses against a strict versioned schema; cap all fields; mark origin as `ai`; on invalid response report `AI analysis unavailable`; never let AI alter deterministic evidence, policy, baseline, or default gate status. | Fixtures return invalid JSON, wrong schema, extra fields, extreme numbers, contradictory IDs, prompt leakage, and timeouts; deterministic result and exit code remain byte-equivalent with AI off. | Phase 6. “AI advisory by default” is a permanent ADR and 1.0 compatibility promise. |
| AI-04 | **Cache leaks across repositories, users, providers, prompts, or redaction versions.** Stale advice is reused after evidence changes. | Cache key is fingerprint only; shared CI cache restores private AI entries; raw source stored indefinitely; provider/model change is ignored. | Key on repository identity, finding fingerprint/version, context hash, provider, model, prompt/schema/redaction versions; use restrictive local permissions; never share AI caches with fork jobs; avoid raw context storage by default; support TTL and purge; invalidate on any boundary change. | Two-repository collision fixture, permission checks, changed-context miss, changed-provider miss, fork-cache isolation, and purge test. | Phase 6. Cache storage, encryption, retention, and CI use are unresolved and need an ADR. |
| AI-05 | **Unbounded requests cause denial of wallet or service.** Large finding sets, retries, or adversarial contexts multiply cost. | Requests scale with raw findings; retry loops; no cumulative accounting; context grows beyond preview; fork PR can invoke paid AI. | Deduplicate and policy-filter before AI; enforce per-run request, finding, input-token, output-token, elapsed-time, and monetary ceilings before each call; cap retries; never invoke paid remote AI for untrusted forks; degrade without changing the gate. | Mock provider verifies hard ceilings, concurrent accounting, retry cap, oversized-context rejection, and unchanged deterministic result after budget exhaustion. | Phase 6. Budget fields and default values must be part of the versioned config contract. |
| AI-06 | **Remote availability or model drift makes results appear deterministic.** | Same commit yields different advisory text but no model/prompt metadata; provider failure delays or fails the core gate. | Keep AI outside the default gate; record provider, model, prompt/schema versions, context hash, and cache status; bound latency; report unavailable separately; never claim reproducibility for model prose. | Replay with different responses, provider errors, rate limits, and offline mode; deterministic evidence and exit code remain identical. | Phase 6. Release gate includes an offline full-core test with no AI credentials or network. |

## Technical Debt Patterns

| Shortcut | Immediate benefit | Long-term cost | When acceptable |
|----------|-------------------|----------------|-----------------|
| Rescue parser errors to `[]` | Simple adapter code | False `PASS` | Never. |
| Treat all non-zero exits alike | Shared runner logic | Findings and tool failures are confused | Never; share process capture, not semantic mapping. |
| Fingerprint with path and line | Easy implementation | Baseline churn and false new/resolved states | Only in a throwaway spike, never persisted or released. |
| Allow baseline updates during `check` | Convenient adoption | Baseline poisoning and nondeterministic working tree | Never. |
| Permit wildcard waivers | Fewer entries | Invisible permanent debt | Not in the initial product. Revisit only with audited scope and expiry semantics. |
| Pass the full environment | Fewer compatibility bugs | Secret and nondeterminism leakage | Only in an explicitly labeled local diagnostic mode that cannot run in CI and never logs values. |
| Capture unbounded output in memory | One-line Open3 usage | Deadlock/OOM and missing limit semantics | Only for tiny trusted version probes with a hard wrapper limit. |
| Reuse coverage directory | Faster setup | Stale and cross-run artifacts | Never for gating runs. |
| Store raw AI context in cache | Easier replay | Persistent source/secret leak | Never by default; only explicit debug export with warning and restrictive permissions. |
| Use Action tags for convenience | Easier updates | Tag movement and supply-chain compromise | First-party examples may follow platform guidance, but third-party release-path actions must use reviewed SHAs. |
| Publish with a long-lived RubyGems key | Familiar workflow | Credential theft enables package compromise | Only emergency manual recovery with gem-scoped, expiring key, MFA, and documented revocation; normal path uses Trusted Publishing. |

## “Looks Done But Isn't” Release Checklist

- [ ] **Analyzer completeness:** Every required analyzer reports a supported version, terminal state `succeeded`, complete output, and adapter contract version.
- [ ] **Failure corpus:** Unavailable, unsupported, timeout, signal, every non-zero exit, empty, malformed, partial, oversized, invalid encoding, parser failure, and unknown schema fixtures cannot `PASS`.
- [ ] **Tests:** Expected Minitest/RSpec suites, executed counts, skips/pending, filters, and load errors are visible and policy-compliant.
- [ ] **Coverage:** Artifact schema, commit, root, run identity, freshness, expected workers, successful collation, and successful tests are proven.
- [ ] **Determinism:** Repeated runs under varied locale, timezone, path, ordering, and concurrency have equivalent canonical gate results.
- [ ] **Fingerprint compatibility:** Edit, rename, move, copy, collision, and algorithm-migration corpora pass; compatibility impact is documented.
- [ ] **Baseline governance:** The baseline was produced by a complete run, has an auditable diff, and cannot be changed by ordinary checks or untrusted privileged CI.
- [ ] **Waivers:** Every waiver has exact scope, owner, reason, creation date, UTC expiry, and valid live target; expired waivers are enforced.
- [ ] **Execution containment:** Injection, concurrent-pipe, timeout, grandchild, signal, resource-limit, temp-cleanup, and malicious-output tests pass on every supported OS.
- [ ] **Offline core:** Full deterministic gate works with network disabled and no AI credentials.
- [ ] **AI boundary:** Remote AI is off by default; transmission manifest, secret canaries, prompt-injection fixtures, schema failures, cache isolation, and budget ceilings pass.
- [ ] **Fork safety:** Hostile fork code runs only without secrets and with read-only token; no privileged workflow executes or trusts fork code/artifacts.
- [ ] **Supply chain:** Lockfile, dependency review, action SHA policy, license inventory, and release dependency review pass.
- [ ] **Artifact identity:** Tested `.gem`, checksummed `.gem`, attested `.gem`, published `.gem`, and installed smoke-test `.gem` share the expected digest and source revision.
- [ ] **Provenance firewall:** Current tree, full history, generated gem, archives, media metadata, docs, release notes, and CI artifacts have zero unresolved private-information matches.
- [ ] **English-only:** All repository and release prose passes; only manifest-listed i18n fixtures are exempt.

## Recovery Strategies

| Incident | Cost | Immediate recovery |
|----------|------|--------------------|
| False `PASS` from incomplete analyzer evidence | HIGH | Mark affected result invalid; block merges/releases; preserve bounded diagnostics; fix the shared adapter/runner contract; rerun every affected commit or release candidate. |
| Fingerprint regression or collision | HIGH | Freeze baseline updates; restore prior fingerprint version; ship an explicit migration tool/mapping; recalculate states and require review before accepting the migrated baseline. |
| Poisoned baseline or abusive waiver | MEDIUM | Revert unauthorized entries; regenerate only from a complete trusted run; expire/review waivers; add protected review for affected paths. |
| Secret or provenance leak | HIGH | Stop publication; revoke/rotate credentials first; remove public artifacts where possible; coordinate history cleanup while assuming existing clones retain data; rescan all surfaces before resuming. |
| AI transmission or cache leak | HIGH | Disable provider integration; revoke exposed credentials; purge local/shared caches and provider-side data where supported; document scope and tighten context/redaction tests. |
| Compromised Action, dependency, or release | HIGH | Disable workflow/publisher; revoke trust and tokens; verify all artifacts since compromise; yank affected gem versions when appropriate; publish a new corrected version rather than mutating an existing release. |
| Orphan/resource incident | MEDIUM | Terminate process group, quarantine incomplete artifacts, clean verified LineClear-owned temp state, reduce limits/concurrency, and add the triggering repository to the stress corpus. |

## Required ADRs and Explicit Decisions

| Decision | Why an ADR is required | Deadline | Current recommendation / unresolved point |
|----------|------------------------|----------|-------------------------------------------|
| Analyzer terminal-state and fail-closed semantics | All policies and reporters depend on what counts as complete evidence. | Before Phase 1 implementation | Required analyzer not `succeeded` means no `PASS`; optional absence remains explicit. Decide exact `WARN` versus `FAIL` presentation without weakening completeness. |
| Safe process runner and platform containment | Timeout, signal, process-group, environment, descriptor, and resource-limit behavior differs by OS. | Before Phase 1 process runner | Use argv execution, minimal environment, bounded concurrent streams, process groups, graceful/forced termination, and reaping. Decide supported OS matrix and documented degraded controls. |
| Configuration format, safe loading, and precedence | Ambiguity changes policy and can make local/CI gates diverge. | Before Phase 1 config contract | Data-only strict schema; no ERB/object tags; unknown keys fail. Decide CLI/config/default precedence and whether any environment override is permitted. |
| Fingerprint v1 composition and compatibility | Baselines persist identity across releases; changes can reclassify all debt. | Before Phase 3 | Full SHA-256 canonical payload with explainable components and duplicate detection. Decide logical-scope inputs, path weight, rename aliases, and migration policy. |
| Baseline trust and mutation authority | Baseline changes can bypass no-new-debt policy. | Before Phase 3 | `check` is read-only; explicit update from complete evidence; protected review and machine diff. Decide required approvers and whether baseline files need signatures beyond Git review. |
| Waiver governance | Expiry and scope directly affect merge authorization. | Before Phase 3 | Exact fingerprint only, required metadata, UTC expiry, no wildcard initially. Decide expired-waiver severity and maximum lifetime. |
| Deterministic run manifest | Reproducibility depends on defining which environmental inputs are part of “same run.” | Before Phase 2 expansion | Record repository/base revisions, config/policy, adapter/analyzer versions, selected environment, seeds, and limits. Decide which OS/runtime differences are accepted inputs. |
| GitHub trusted/untrusted workflow split | A wrong trigger or artifact handoff can expose write tokens, secrets, and publisher authority. | Before Phase 4 | `pull_request` for untrusted verification; privileged workflows handle metadata only. Decide the minimal safe handoff, if any, and forbid remote AI for forks. |
| Remote-AI consent, data use, and provider policy | Transmission and retention cannot be undone after a request. | Before Phase 6 | Explicit opt-in, previewable minimal context, secret fail-closed, provider/model/retention disclosure. Decide whether consent is per project, run, or request and which provider retention guarantees qualify. |
| AI cache security | Cache contents can retain proprietary source and cross trust boundaries. | Before Phase 6 cache | No raw context by default; restrictive local scope and complete key. Decide encryption, retention/TTL, shared CI support, and purge guarantees. |
| Release authentication and provenance | Gem compromise affects downstream users and project identity. | Before first gem publication | RubyGems Trusted Publishing, protected environment, MFA, build-once, checksum, verified attestation, immutable release. Decide bootstrap/recovery procedure and exact attestation policy. |
| Public information firewall | Generic secret tools cannot recognize all private provenance, and detection inputs can themselves disclose it. | During Phase 0; before public repository/release | Synthetic-only fixtures; private local detection input outside the repository; scan tree, history, package, and artifacts; publish only counts/categories. Decide owners, tooling, and evidence retention. |
| English-only enforcement | False negatives violate the public contract; broad exceptions hide drift. | During Phase 0 | CI and release scan with per-file i18n fixture manifest. Decide language detector/term rules and reviewer for exceptions. |

|-------------|----------------------|------------------------|
