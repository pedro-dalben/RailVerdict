# RailVerdict 1.5 — Stage 0 & 1 Product Gap Investigation
**Date:** 2026-08-27  
**Starting Baseline:** RailVerdict 1.4.0 (commit `87a9e36`, tag `v1.4.0`)  
**Primary Real Consumer:** `IntegrarPlus`  
**External Validation Lab:** `railverdict-lab` (132/132 scenarios PASS)

---

## 1. Executive Summary & Context

RailVerdict 1.4 established reliable, fail-closed evidence acquisition, cryptographic Verification Receipts, immutable repository state identity, and cross-agent Handoff packets. Dogfooding against `IntegrarPlus` (a production Rails application with 132 models, 145 controllers, 481 templates, and 3,859 RSpec examples) confirmed:

- **Correctness & Reliability:** High. Trust invariants hold; no false PASS.
- **Baseline / No-New-Debt:** Highly valued by engineering teams.
- **Verification Receipt:** Effective for provenance and auditability.
- **Current Advisory Recommendation:** IntegrarPlus maintains RailVerdict in `mode: advisory` rather than `strict`.

### Why Advisory Mode Persists
1. **CI Time Savings Were Negligible:** When dynamic test verification (`rspec`, `simplecov`) is required, whole-set Handoff reuse evaluates to `VERIFICATION_REQUIRED`, forcing a complete rerun of all analyzers (RuboCop, BundlerAudit, RSpec, SimpleCov) and saving 0 seconds on CI.
2. **Changed Mode Ran the Full Suite:** In `changed` scope, RailVerdict ran the entire 3,859 RSpec test suite (~325s vs ~326s for full verification), yielding no acceleration for pull request feedback.
3. **Critical Rails-Native Checks Remained Outside the Gate:** Security scanning (`brakeman`) and database consistency (`database_consistency`) were executed outside the unified RailVerdict merge gate.
4. **Redundant Finding Identifiers:** RSpec findings produced double prefixes (`rspec/rspec/example:...`).

The objective of RailVerdict 1.5 is **Rails-Native Adoption & CI Efficiency**: transform RailVerdict from an evidence acquisition wrapper into a practical Rails-native verification control plane that delivers tangible developer velocity without compromising deterministic verification trust.

## 3. Workstream A: Rails Security Analysis (Brakeman)

### Upstream Interface & Capabilities
- **Invocation:** `brakeman -q --no-pager -f json -o <output_file>`
- **Exit Codes:**
  - `0`: Clean scan (0 warnings).
  - `3`: Warnings detected (standard Brakeman behavior with exit-on-warn).
  - Other non-zero: Fatal execution failure (syntax error, unsupported Ruby, crash).
- **Supported Version Range:** Gem requirement `>= 7.0, < 9` (matches modern Rails 7/8 ecosystems; 8.0.6 verified in IntegrarPlus).
- **JSON Structure:** Root contains `scan_info` (with `brakeman_version`, `ruby_version`, `rails_version`, `security_warnings`), `warnings` array, `errors` array, `obsolete` array.

### Normalization Contract
- **Category:** `security`
- **Severity Mapping:**
  - Brakeman `High` $\rightarrow$ `high`
  - Brakeman `Medium` $\rightarrow$ `medium`
  - Brakeman `Weak` $\rightarrow$ `low`
- **Confidence Mapping:**
  - Brakeman `High` $\rightarrow$ `high`
  - Brakeman `Medium` $\rightarrow$ `medium`
  - Brakeman `Weak` $\rightarrow$ `low`
- **Rule ID:** Standardized to canonical rule ID `check_name` (e.g. `SendFile`, `SQL`, `LinkToHref`) with `analyzer: "brakeman"`.
- **Location:** Normalized repository-relative path, line number (`start_line`, `end_line`).
- **Evidence Reference:** `native:brakeman:<fingerprint_prefix>`.
- **Exit Code Reconciliation:** Exit code 0 or 3 with valid JSON and warnings array matching counts succeeds with findings; missing output or non-zero exit without structured document fails closed as `failed` or `malformed`.

### Decision
**Implement native `RailVerdict::Analyzers::Brakeman` in 1.5.**

## 4. Workstream B: Rails Database Consistency (`database_consistency`)

### Upstream Analysis (Gem v3.0.9)
Inspection of `database_consistency-3.0.9` gem source revealed:
1. **CLI Capabilities:** Only supports `-c`, `-g` (generate-todo), `-f` (autofix), `--only-checkers`, `-h`. **No `--format json` or machine-readable format exists.**
2. **Execution Model:** Requires full Rails environment boot (`require config/boot`, `require config/environment`, `Rails.application.eager_load!`) and an active, live database connection to query database metadata and compare with ActiveRecord reflection.
3. **Output Contract:** Uses `DatabaseConsistency::Writers::SimpleWriter`, which writes unversioned, human-formatted terminal strings with ANSI codes directly to `stdout`.

### Trust Assessment
- **Product Rule:** `NO STRUCTURED CONTRACT = NO FAKE STRUCTURED ANALYZER.`
- Attempting to regex-parse human stdout would create a fragile, unversioned, high-risk integration prone to false confidence and breakage across gem patches.
- Furthermore, forcing a database connection during RailVerdict verification conflicts with RailVerdict's lightweight offline/local-first verification model for static checks.

### Decision
**Defer native `database_consistency` analyzer.** Upstream lacks a versioned structured JSON contract. Return a design conclusion documenting the gap and establish criteria for future adoption (structured JSON output and non-mutating offline schema inspection).

## 5. Workstream C: Changed-Scope RSpec (Targeted vs Full Test Verification)

### The Problem
In RailVerdict 1.4, running `railverdict check --changed` on a 1-line model change in `IntegrarPlus` ran the entire 3,859 test suite (~325s). Developers received no velocity benefit.

### Test Impact Strategies Evaluation
1. **Direct Convention Mapping:**
   - `app/models/user.rb` $\rightarrow$ `spec/models/user_spec.rb`
   - `app/controllers/users_controller.rb` $\rightarrow$ `spec/requests/users_spec.rb`, `spec/controllers/users_controller_spec.rb`
   - `app/services/process_payment.rb` $\rightarrow$ `spec/services/process_payment_spec.rb`
   - Direct spec edits: `spec/models/user_spec.rb` $\rightarrow$ `spec/models/user_spec.rb`
2. **Multi-Location Convention Resolution:**
   - Expand `RailsContext::Resolvers::TestCandidates` to resolve models, controllers, services, policies, jobs, mailers, helpers, components, and views to their matching RSpec locations (`spec/models/`, `spec/requests/`, `spec/controllers/`, `spec/services/`, `spec/policies/`, `spec/jobs/`, `spec/mailers/`, `spec/helpers/`, `spec/components/`, `spec/views/`, `spec/system/`).
3. **Trust Semantics: FULL vs TARGETED Verification Scope:**
   - **Critical Invariant:** RailVerdict MUST NEVER report a heuristic test subset as "FULLY VERIFIED".
   - Introduce explicit `test_scope`:
     - `full`: Complete test suite executed. Full verification assurance.
     - `targeted`: Heuristically selected test subset executed. Valid targeted verification; receipt and gate explicitly record `test_scope: "targeted"`.
4. **Safe Fallback to Full RSpec Suite:**
   Targeted selection must fall back to running the full RSpec suite whenever:
   - Shared infrastructure or framework files change: `spec/spec_helper.rb`, `spec/rails_helper.rb`, `spec/support/**`, `Gemfile`, `Gemfile.lock`, `config/**` (`routes.rb`, `application.rb`, initializers, environments), `db/schema.rb`, `db/migrate/**`, `app/models/application_record.rb`, `app/controllers/application_controller.rb`, `app/jobs/application_job.rb`, `app/mailers/application_mailer.rb`.
   - Ambiguous or unknown dependencies: a changed file in `app/` or `lib/` yields zero existing test candidate files.
   - User or policy configuration explicitly requests `test_scope: full` or full verification mode.
5. **Adversarial Safety:**
   - If a change in `app/models/user.rb` introduces a regression in `spec/services/order_processor_spec.rb`: in targeted mode, only `spec/models/user_spec.rb` runs and passes. RailVerdict reports `PASS` with `test_scope: targeted` and records the targeted file set in `evidence_summary`. The Verification Receipt explicitly declares `test_scope: "targeted"`. Downstream merge policies requiring full verification will require `test_scope: full`.

### Decision
**Implement Targeted RSpec Execution with conservative safe fallback and explicit `test_scope` (full vs targeted) metadata.**

## 6. Workstream D: Per-Analyzer / Tiered Evidence Reuse

### The Problem in 1.4
In RailVerdict 1.4, `Reuse.evaluate` operates on an all-or-nothing whole-set basis. When dynamic test evidence (`rspec`, `simplecov`) is required on CI, the entire handoff is rejected with `VERIFICATION_REQUIRED`, re-executing RuboCop and BundlerAudit even when their inputs, tool versions, and repository state were completely unchanged.

### 1.5 Architecture: Per-Analyzer Decisions & VerificationPlan
1. **Per-Analyzer Decision Engine:**
   Evaluate each required analyzer independently:
   - `REUSABLE`: Previous evidence in Handoff/Receipt is fresh, analyzer version matches, configuration matches, input files unchanged.
   - `VERIFICATION_REQUIRED`: With canonical reason code (`repository_scope_changed`, `tool_version_changed`, `advisory_database_changed`, `policy_requires_execution`, `required_analyzer_missing`, `evidence_incomplete`).
2. **Deterministic `VerificationPlan`:**
   Construct an explicit plan before execution:
   ```
   VerificationPlan:
     reuse:    [rubocop, bundler_audit]
     execute:  [rspec, simplecov]
     fallback: none
     test_scope: targeted (or full)
   ```
3. **Selective Execution & Fresh Gate Evaluation:**
   - Execute ONLY the analyzers in `plan.execute`.
   - Combine reused `AnalyzerResult` records and findings with newly produced `AnalyzerResult` records.
   - Re-evaluate current baseline, current waivers, and current policy against the unified evidence set.
   - **Invariant:** ALWAYS construct a brand NEW `GateResult`. NEVER reuse an old `GateResult`.

### Decision
**Implement Per-Analyzer Evidence Reuse and the `VerificationPlan` abstraction.**

## 7. Workstream E: Finding ID Cleanup (`rspec/rspec/...`)

### Investigation & Root Cause
- In `lib/rail_verdict/analyzers/rspec.rb:225`:
  `rule_id = "rspec/example:#{id}"`
- In `lib/rail_verdict/findings_command.rb:20`, `sarif.rb:121`, `github_annotations.rb:24`:
  Reporters constructed display names as `"#{finding.analyzer}/#{finding.rule_id}"`.
- For RSpec findings, this produced `"rspec/rspec/example:..."`.
- Similar duplication existed in `minitest` (`"minitest/minitest/test:..."`) and `bundler_audit` (`"bundler_audit/bundler_audit/advisory:..."`).
- In contrast, RuboCop produced `"Layout/LineLength"` $\rightarrow$ `"rubocop/Layout/LineLength"`.

### Safe Remediation Plan
1. **Canonical Rule ID Normalization:**
   - RSpec: `rule_id = "example:#{id}"`
   - Minitest: `rule_id = "test:#{class}##{method}"`
   - BundlerAudit: `rule_id = "advisory:#{id}"`
   - Brakeman: `rule_id = check_name` (e.g. `SendFile`)
2. **Reporter Formatting Defense:**
   In reporters, ensure `rule_id` is prefixed with `analyzer/` only if `rule_id` does not already start with `analyzer/` or `analyzer:`.
3. **Baseline Backwards Compatibility:**
   In `Comparison` and `Fingerprint`, provide legacy alias matching for existing baselines generated with `1.4.0` so existing baseline files match seamlessly without migration churn.
