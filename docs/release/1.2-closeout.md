## 4. Verification protocol

| Symbol | Meaning | Exit |
|---|---|---|
| `PASS` | Complete verification, policy allows merge (`no_new_debt`: zero introduced findings) | 0 |
| `WARN` | Complete, non-blocking advisory only | 0 |
| `FAIL` | Complete, policy rejected (`introduced` blocking findings) | 1 |
| `INCOMPLETE` | Evidence missing / operational failure / invalid inputs — no trustworthy gate | 2 |
| `INTERRUPTED` | `SIGINT` after child cleanup | 130 |

`INCOMPLETE` vs `FAIL` vs `STALE` are three different facts: a fresh `FAIL` is a verified rejection; a fresh `INCOMPLETE` is unverified; a `stale` says nothing about the current state.

**Freshness verdicts (receipt):**

| Status | Meaning |
|---|---|
| `fresh` | Current observable state is identical to the verified state (all bound dimensions equal) |
| `stale` | At least one identity component changed; deterministic `reasons[]` listed |
| `invalid` | Document failed integrity / schema / version check (`receipt_integrity_failed`, `receipt_malformed`, `receipt_schema_invalid`, `incompatible_receipt_version`, `receipt_too_large`, `receipt_unreadable`) |
| `unavailable` | Current state could not be determined fail-closed (`repository_state_unavailable:*`) |

Create mirrors gate exits (`0` PASS/WARN complete, `1` FAIL complete, `2` INCOMPLETE/unavailable, `130` interrupt); `verify` maps fresh+original gate to same values and any stale/invalid/unavailable/fresh-INCOMPLETE to `2`.

### Freshness decision (approved semantic)

**`fresh` means the current observable repository state together with the resolved verification environment is equivalent to what produced the receipt — specifically, HEAD, the Git index snapshot digest, the worktree-vs-index delta digest (with per-path content hashes), and the resolved `configuration`/`baseline`/`waivers` content digests are all byte-identical, and `railverdict_version` and `ruby_version` match; `analyzer_versions` is only part of freshness when the caller supplies fresh versions to `Receipt.validate_freshness` (otherwise it is bound in the `receipt_id` but not required to remain identical for `fresh`). This is option B with explicit, bounded, cheaply-observable dimensions (git plumbing + file digests + version strings) and no timestamp/absolute-path/mtime dependence, chosen because it preserves determinism, offline operation, multi-clone identity, and agent handoff without costly re-observation of analyzers, while still failing closed on every repository mutation and flagging analyzer drift when supplied — a precise `fresh` that never hides stale evidence but tolerates analyzer-only drift as `fresh` unless the caller opts into stricter `analyzer_environment_changed` detection.**

## 5. Receipt trust model

**What a receipt proves:**

- The exact observable repository state that was verified (HEAD + Git index snapshot + worktree-vs-index delta with per-path content hashes + resolved `configuration`/`baseline`/`waivers` digests) as captured by `RepositoryState` v1 in a single canonical digest `sha256:<hex>` over `CanonicalJSON`.
- The verification environment bound at issuance (`railverdict_version`, `ruby_version`, `analyzer_versions` canonicalized to `unknown` when absent).
- The verification mode (`full`/`changed` with `base`/`merge_base`) and the stable `GateResult` projection (statuses, `findings` sorted by `fingerprint`, `analyzer_evidence` sorted by `analyzer`, `operational_failure_codes` + `decision_reason_codes` sorted, volatile `duration_seconds`/`seed` excluded).
- Optional PR Intelligence binding as `sha256:` over its stable projection and optional `RepairPacket` linkage via `packet_id`.
- Determinism: `receipt_id = sha256:<64hex>` over canonical identity fields (excluded from its own payload); no `created_at`; timestamps/durations/seeds/absolute paths/diagnostics/AI output excluded by design.
- Snapshot guard: `pre == post` else `repository_changed_during_verification` and no trusted current-state receipt is issued.

**What a receipt explicitly does NOT prove:**

- Authorship or signing: `receipt_id` is content identity only. An actor who can rewrite the whole document and recompute `sha256` can forge a self-consistent receipt. No HMAC, PKI, Sigstore, or remote attestation in 1.2.
- Advisory AI output, volatile test timing, temporary paths.
- That the repository was ever private or that the gem was installed from a specific registry — only that the verified state digest matches.
- When adversarial forgery is in scope, a trusted CI/orchestrator that independently runs RailVerdict is the trust anchor. Receipts remain integrity records until signing/attestation is added in a future milestone.

## 6. Freshness identity matrix

| Dimension | Stored in Receipt | Checked by `receipt verify` (CLI) | Checked by MCP (`get_verification_receipt`/`get_pr_intelligence` via `Cache`) | Can produce `stale` |
|---|---|---:|---:|---:|
| HEAD (full SHA or `unborn`) | Yes (`repository_state.head`) | Yes (`head_changed`) | Yes (via `state_digest` which includes HEAD) | Yes |
| Git index snapshot (`ls-files -s` digest) | Yes (`index_digest`) | Yes (`index_changed`) — catches staged-only mutations | Yes (via `state_digest`) | Yes |
| Worktree-vs-index delta (`status --porcelain=v2` + per-path content `sha256` for files/symlinks) | Yes (`worktree_digest`) | Yes (`worktree_changed`) — untracked, symlink, deleted, directory all bound | Yes (via `state_digest`) | Yes |
| Configuration file content (`sha256:`) | Yes (`configuration_digest`) | Yes (`configuration_changed`) — EFFECTIVE path via `Check.effective_input_paths` | Yes (via `state_digest` with effective paths) | Yes |
| Baseline content (`sha256:` or `null`) | Yes (`baseline_digest`) | Yes (`baseline_changed`) — effective path | Yes | Yes |
| Waivers content (`sha256:` or `null`) | Yes (`waivers_digest`) | Yes (`waivers_changed`) — effective path | Yes | Yes |
| RailVerdict version | Yes (`railverdict_version`) | Yes (`railverdict_version_changed`) | Checked only via `Cache.valid?` / `environment_digest` (not via `fresh_entry` state check) — see §7 | Yes (CLI) / env-drift in MCP `valid?` only |
| Ruby version | Yes (`environment.ruby_version`) | Yes (`ruby_version_changed`) | Same env caveat | Yes (CLI) |
| Analyzer versions (canonical `"unknown"` when nil/empty) | Yes (`environment.analyzer_versions` sorted, canonical) | Only if caller supplies `current_analyzer_versions` → `analyzer_environment_changed`; CLI `verify` does not supply fresh versions, so drift not flagged as `stale` by default | Same — `Cache` `fresh_entry` ignores env, `valid?` checks env | Conditional |
| Changed base (`base` SHA) | Yes (`changed_scope.base`) | Bound into receipt identity (different mode/base → different `receipt_id`) but not a separate stale reason | Bound via state+mode | Via `receipt_id` mismatch (`invalid`) |
| Merge base | Yes (`changed_scope.merge_base`) | Bound into receipt identity | Bound | Via `receipt_id` |
| PR Intelligence | Digest over stable projection (`pr_intelligence.digest`) | In identity (not a freshness reason; `pr_intelligence_unavailable` is a derived status) | Via cached doc; stale refuses | No (identity) |
| RepairPacket | Linkage (`repair.packet_id`) | In identity only; boundary changes surfaced by `verify_repair`'s `verification_boundary_changed` and by staleness of any baseline/waiver/config mutation | — | No (but mutation after FAIL makes that FAIL receipt `stale` via baseline/waiver/config digest) |

**Canonical current-state resolution:** `Check.effective_input_paths` → `RepositoryState.capture` → `Receipt.validate_freshness` / `MCP::Cache`. Both `receipt create` and `receipt verify` (and MCP `Cache.configuration_paths_for`) resolve the EFFECTIVE `config`/`baseline`/`waivers` paths honoring `configuration.baseline.path`/`waivers.path` plus CLI/MCP overrides, all contained via `PathSafety`/`RepositoryRoot.contained?` (symlink-aware realpath prefix). Custom paths are content-bound into the receipt; a gitignored or out-of-root input cannot silently participate — it is either digested or the command is refused (`repository_state_unavailable`).

**MCP consistency:** one `verify` executes analyzers exactly once under a mutex; `get_verification_receipt` and `get_pr_intelligence` never rerun them and read the cached canonical outcome. Stale cache is refused as `verification_required`/`stale` with explicit `code`, never returned as `fresh`. See `lib/rail_verdict/mcp/cache.rb` (`state_digest` + `environment_digest`, `fresh_entry` vs `valid?`).

## 7. Known limitations

- **Analyzer environment drift:** `fresh` by default means "current observable repository state is identical to the verified repository state" plus Ruby/RailVerdict version. Analyzer version drift is only flagged as `stale` (`analyzer_environment_changed`) when the caller supplies fresh analyzer versions to `Receipt.validate_freshness`. A RubyGems/SDK upgrade that changes `rubocop`/`rspec` without touching the repository will still verify as `fresh` via CLI/MCP unless the caller re-derives fresh versions. Documented as non-blocking; mitigation is to re-verify after analyzer upgrades. False-fresh risk is low (analyzer change cannot invent a `PASS` over new findings without re-running, but can mask changed detection).
- **Waiver-injection via MCP `verify_repair`:** `RVLAB-16` — adding a waiver after a blocking finding and calling `verify_repair` still reports `gate: PASS` (`target_status: still_present`, `verification_boundary_changed: {waivers:true}`). Mitigated in 1.2 by receipt staleness (`waivers_changed` makes the prior FAIL receipt stale) and by `verify_repair`'s `verification_boundary_changed` being visible, but not yet a hard gate rejection. See Lab findings register.
- **Snapshot non-linearizability:** `pre`/`post` captures are not atomic with analyzer I/O — a mutate-and-revert inside the verification window can be missed (documented in ADR 0016).
- **Bounds:** index `8 MiB`, status `4 MiB`, `500` dirty paths, `2 MiB` per hashed file, receipt `256 KiB`, index/worktree/status truncation → `unavailable`.
- **No Brakeman, no OS sandbox, no full semantic graph, no autonomous mutation, no signing** — per 1.0/1.1 charter, unchanged.
- **No analyzer CLI timeout overrides** — `timeout_seconds` is config-only (`1..3600` per analyzer, default `30s`), validated via `configuration-v1.5`.
- **Qualified trademark / jurisdiction / private-provenance scan:** `FOUNDATION_PRIVATE_PATTERNS` remains `NOT RUN` by design; publication was `NON-BLOCKING BY MAINTAINER DECISION 2026-08-19` — not legal clearance.
