# RailVerdict 1.2.0 — Release Identity

**Date:** 2026-08-24 (updated to include post-tag audit commit 964c685)
**Author:** launch readiness + launch engineering

## Question

The launch audit reported an apparent discrepancy:

```
audited/final commit: 964c6859c99dac3003696e77d7082eff0b2a4ada
v1.2.0 tag:           d49c204b36fe89a6fcf5f22fd4c42978362b10d2
RubyGems SHA-256:     d8e848b1e72585b7f583a85d2a67e25b472bd1860549d1d4330c8a33104f82e9
```

Are 964c685 and d49c204 different releases? Is the published gem stale or missing a correctness fix?

## Answer (one paragraph)

**No correctness gap.** The published RubyGems artifact was built from the `v1.2.0` tag target `d49c204` via the `release.yml` build-once OIDC workflow. Commit `964c685` is a **documentation-only** follow-up on `master` after the tag (README/contract wording + launch-evidence reports). It introduces **zero runtime code, zero schema, zero gemspec, zero analyzer, zero policy changes**. Lib and schemas are byte-identical between the two commits; the gem built at 964c685 differs only because `spec.files` includes `README.md` (which received the version-drift fixes). The published artifact therefore does **not** contain the three README/contract phrasing fixes, but those fixes are editorial (confusion reduction), not security/correctness, and no `READY_TO_PUBLICIZE` runtime fix is missing.

## Decision

- **Do not move the tag.** Rewriting `v1.2.0` would invalidate provenance (CI logs, RubyGems attestation, Lab candidate `source_sha d49c204`) for cosmetic gain.
- **Do not cut 1.2.1.** No runtime/security/correctness fix is missing; the doc drift (confusing `1.0.1` phrase, Brakeman `1.0`, stale 21/21 table) is corrected on the default branch and will ship in the next patch/minor gem that touches README. If a correctness bug appears, follow `docs/roadmap/1.3-evidence-backlog.md` patch policy.
- **Documentation of the relationship:** this file. `CHANGELOG.md`, `docs/release/1.2-launch-report.md`, and `README.md` on master now reflect `1.2.0` correctly; the RubyGems README rendered from the published gem still shows the pre-fix `1.0.1` phrase until the next publish, which is acceptable.
